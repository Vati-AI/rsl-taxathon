## Differences

Per-taxpayer and per-claim differences between the platform read-back and the standalone run (time excluded): 0 (none). Read-back gaps: 0 cases without a completed run, 0 taxpayers whose cases disagree on a check summary.

### Every difference, explained

- **Detection, lanes, amounts, recompute and routes: no difference.** All 4185 claims got a lane proposal and every case a `completed` run. The scorer saw the same flags, findings and routes, lanes and amounts, and check counts as the standalone run of the same 200 taxpayers. Those are also the numbers committed by TAX-118. Both ran the TAX-118 check files unchanged (rule fingerprint equal to the freeze), with the same inputs. The RSL records came from the same sealed world, through the site's recorded fixture. The taxpayer's records were round-tripped through a stored CSV evidence document and re-hashed before use.
- **Time: about 0.95 s against 0.013 s per taxpayer (mean).** Live time is the `Vati Assurance Run.seconds` of the taxpayer's cases, summed. Each case is one claim, and each case re-runs the whole taxpayer assessment, so a taxpayer with 24 claims pays for it 24 times. Each run also includes reading the records document, parsing it and recording findings, a lane proposal and the run itself in Frappe. The first case in the worker process also loads the 38 MB fixture file. The standalone figure is check time only, run once per taxpayer. The end-to-end wall time is a separate measure: 183 s of seeding, a 476 s outbox drain (which also includes the failing Jube attempts) and 26 s of read-back for 4185 claims.
- **How the platform read-back is reshaped for the scorer** (it is not a change in the numbers). The scorer counts some lists without reading them: recompute comparison rows and findings, three-way rows and work-arrangement referrals. These counts come from the check summary stored on each `Vati Assurance Run`, and every case of a taxpayer agreed on them (0 mismatches). Findings are deduplicated per taxpayer by subject, because each case of a taxpayer records the same taxpayer-level findings. The fake-invoice amount is the disputed amount of lane proposals with an authenticity indicator. The imported-services gap is the three-way total in the run summary.
- **Jube: unavailable.** It was not running or configured on the disposable site. Every case's `case.registered` step ended as `dead_letter` (1200), `retry` (2815) or `pending` (170), with code `jube_not_configured`. The assurance step is the case's first event, so it never waited on Jube. Nothing about Jube is reported as clean. OpenAleph, yente and Docling were not used by this step and not configured on the site.
