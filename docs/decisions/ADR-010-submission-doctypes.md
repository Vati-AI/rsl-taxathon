# ADR-010: Submission and tax-domain DocTypes, money and periods

Status: proposed (TAX-031, pending human review)
Owner and task: Edga (owner), TAX-031; implemented by keletso-claude-code on Keletso's instruction
Date: 2026-11-04

Context and smallest prototype need: ADR-001 makes Frappe the authority for taxpayer submissions. DATA_MODEL.md lists Taxpayer, Submission and VATReturn/RefundClaim, and the TAX-024 scenarios need imported services (SYN-004). The portal (TAX-043) needs real records for its claim form. TAX-039 will turn a submitted claim into a Jube case (`CreateCaseRequest`). Money must never be a float. Taxpayer A must not reach taxpayer B's figures (V1_ACCEPTANCE).

Decision:

- Five `vati_tax` DocTypes in the `Vati Tax` module: `Vati Taxpayer` (name = `taxpayer_id`), `Vati Submission` (name = `submission_id`), `Vati VAT Return` (one per `vat_return` submission), `Vati Refund Claim` (one per `refund_claim` submission) and `Vati Imported Service` (many per `vat_return`/`withholding_return` submission). All names are UUIDs, generated when omitted. Every DocType carries `tenant_id` and `taxpayer_id`, so the ADR-007 wildcard hooks isolate them with no extra hook code. Detail records must match their submission's tenant and taxpayer. A mismatch, or a reference to another taxpayer's submission or return, is `invalid_reference` (422), the same as a missing one.
- Pure rules live in `vati_tax.submissions.domain` and are tested without a bench. `guard.py` and `declaration.py` apply them in the controllers.
- Money: Frappe `Currency` columns (MariaDB `DECIMAL(21,9)`, `options: currency`) plus a `currency` field fixed to `LSL`. Frappe casts Currency values with `flt()` only when it writes to the database (`get_valid_dict`/`_fix_numeric_types`). That happens after the controller `validate`, so `validate` parses the raw value strictly to a 2-decimal `Decimal`. Malformed strings (`abc`, `1e5`, `12,50`, `1.234`), NaN, infinity, booleans, negatives and values of 10^12 or more are rejected (422 `invalid_domain_input`) instead of being cast to 0. The cap keeps every accepted value exact when Frappe's read path returns it as a float. Callers convert reads with `Decimal(repr(value))` or `domain.parse_money`. Amounts in the API are decimal strings.
- Periods: `YYYY-MM` (the API contract form) or `YYYY-Qn` (the TAX-024 scenarios use `2025-Q4`). The server derives `period_start`/`period_end`. A period may not start in the future or before 2000. It is set once per submission, and details copy it.
- Status (Frappe-owned): `draft` -> `submitted` (taxpayer; needs the declaration and the required figures) -> `correction_needed` (auditor or supervisor, with a taxpayer-facing reason) -> `submitted`. `draft` -> `withdrawn` (taxpayer). Operators may take only these transitions. Figures can be created, changed or deleted only while the submission is `draft` or `correction_needed`, by anyone. Case, risk and investigation state stay in Jube. The submission stores only a write-once `case_id`, set by the service identity.
- Field-level writes per actor (the ADR-007 hooks cover records, not fields): the taxpayer changes only its declaration, contact email and status. Staff change only status and `correction_reason`. The service identity sets only `case_id`. Server fields (`reference`, `version`, `submitted_at`/`by`, period dates, keys, `net_vat`, `tin_masked`) are refused when a client sends a changed value. Declared figures are written only by the taxpayer or an operator. Staff and service roles get read DocPerms on figures.
- Idempotency: an optional `idempotency_key` on a submission gives a unique `submission_key` = SHA-256(tenant, taxpayer, key) (the same hash-column technique as ADR-006). A retried create fails with `UniqueValidationError` and does not create a second draft. Request digests and replay responses are left to the portal API (TAX-043).
- `Vati Taxpayer` keeps a synthetic `tin` (6-15 digits, unique per tenant through `tin_key`) and the contract's `tin_masked`. `taxpayer_type` uses the contract `TaxpayerType` enum.

Alternatives and tradeoff:

- Child tables for return lines and imported services: Frappe checks them through the parent, but they cannot be addressed or linked to evidence on their own, and they sit outside the tenant convention (`scope_of` skips tables). Rejected.
- Data fields with decimal strings for money: exact end to end, but desk forms, reports and DB sums lose numeric types. Currency plus strict validation keeps the DB exact (DECIMAL) at the cost of float reads in Python, which are bounded and converted.
- Frappe Workflow for status: adds DocTypes and fixtures, and does not express per-tenant membership roles. A small transition table in pure code is testable without a bench.
- Monthly-only periods: match `CreateCaseRequest`, but contradict the TAX-024 data. TAX-039 must map quarterly submissions (or the contract widens).

Official sources and version/date checked (2026-11-04): Frappe Framework v16.54.0 (`integration/frappe-framework.lock.json`). Source read in the pinned bench: `frappe/model/document.py` (`insert`/`_save` order, `run_before_save_methods`, `_validate_mandatory`, `validate_set_only_once`, `get_valid_dict`, `_fix_numeric_types`). Observed on that version: `set_only_once` also refuses the first set of an empty field, so `case_id` is write-once in the controller instead. https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes

With the two tenant hooks disabled, the new isolation tests failed (14 failures), so they depend on the hooks.

Consequences and revisit trigger: TAX-043 builds the claim form on these DocTypes and adds request-digest replay. TAX-032 evidence records reference `submission_id`, and figures reference evidence by `evidence_ids`. TAX-039 sends submitted claims to Jube, stores `case_id` and maps quarterly periods. TAX-046 may set `correction_needed`. Revisit if non-LSL amounts or PAYE/withholding figures are needed, or if Frappe changes when numeric casting happens.
