# ADR-015: Audit ledger, overrides and review-only integrity signals

Status: proposed (TAX-059, pending review)
Owner and task: Leseli (owner, reassigned from Edga in #129), TAX-059; implemented by leseli-claude-20261104-059. Backend area review: Edga.
Date: 2026-11-04

(ADR-012 is reserved for TAX-036 and ADR-014 is used on another open branch, so this takes ADR-015.)

Context and smallest prototype need: PROPOSAL.md section 18 asks for an audit trail of who accessed a case, who changed information, who approved actions and where controls were overridden. Repeated unusual overrides or separation-of-duties violations should reach an authorised supervisor as review signals, never as accusations. TAX-046 (ADR-013) added `Vati Audit Event` for decision and evidence-request events, with the case version and a payload hash. It records no reads, overrides or refused attempts, and nothing shows that a row was changed afterwards. TAX-060 (management view) and TAX-077 (integrity views) need a read contract on top of this.

Decision:

- Extend `Vati Audit Event` into the tenant ledger instead of adding a second log. Each entry gets a `category` (`read`, `write`, `approval`, `override`, `denied`), an optional `target_actor` and `reason`, and a place in one SHA-256 hash chain per tenant: `chain_seq` (from 1), `prev_hash` (the previous entry's hash, or 64 zeros) and `entry_hash` over the entry's fields and `prev_hash`. `chain_key` (tenant and position) is unique. `case_id` becomes optional, because ledger reads have no case.
- Sealing happens in one place, `vati_tax.audit.ledger.append`, with no Frappe import. The Frappe store reads the tenant head `for update`, so writers in one tenant queue rather than fork the chain. If an insert clashes after the head moved, it retries at the new head. A clash with an unchanged head (for example the TAX-046 case-version key) is raised as before. The controller recomputes `entry_hash` on insert and refuses a mismatch, and it refuses all edits and deletes. `verify_chain` recomputes the chain and reports `hash_mismatch`, `broken_link`, `missing_entry` or `duplicate_position` by position, without echoing content, so a row changed directly in the database is found.
- What is recorded: every TAX-046 decision and evidence-request event (the decisions repository seals them, keeping their case-version keys); `case.read` from `get_case_review_state`; `evidence.read` from `get_evidence`; `ledger.read` for every ledger view; `override.<control>`; and `<action>.denied` for any refused decision, override or ledger action. Reads come from GET requests, which Frappe does not commit, so the binding commits the read entry. A refusal rolls back, to a savepoint taken just before the call, anything the refused call wrote. It then writes and commits the refusal entry and raises `PermissionError`.
- Overrides: `override.record` is a new action for supervisors that a service identity can never hold. A supervisor records an exception to a named control (`case_assignment`, `evidence_due_date`, `risk_rating`, `playbook_step`) with a reason of 20 to 2,000 characters. Nobody records an override on their own work (`target_actor` equal to the caller). Repeating the idempotency key returns the stored entry, and a changed body is `idempotency_conflict`. This task records the exception. The task that owns each control (TAX-065 playbooks, case assignment) decides what the exception permits.
- Restricted access: `ledger.read` is a new action for supervisors only, never a service identity. Desk read on `Vati Audit Event` is limited to `Vati Supervisor` (plus System Manager), and the TAX-029 tenant query still narrows it to the supervisor's tenants. Officers keep seeing a case's decision trail (write and approval entries) through `get_case_review_state`, as in TAX-046.
- Integrity signals are review prompts: `repeated_overrides` (3 or more by one actor in the window), `repeated_separation_of_duties_attempts` (2 or more refused self-approvals or overrides) and `ledger_integrity` (a broken chain). Each carries `status: review_only` and a note that it is not a finding against any officer. Signals change nothing. A supervisor never sees signals about themselves; `withheld_about_viewer` counts them so another supervisor can look. The window runs from 1 to 365 days (default 30).
- Read contract (whitelisted in `vati_tax.audit.api`, all supervisor-only, all recorded as reads):
  - `get_ledger(case_id?, actor?, category?, since_seq=0, limit=100)` returns entries oldest first, `next_since_seq` and `chain_head`;
  - `verify_ledger()` returns `intact`, `entries_checked`, `head_seq`, `head_hash` and `problems`;
  - `get_integrity_signals(window_days=30)` returns signals and `withheld_about_viewer`;
  - `get_ledger_summary(since, until)` returns `entries`, `by_category`, `by_action`, `distinct_actors`, `ledger_intact` and `head_seq`, for TAX-060.
- Migration: `vati_tax.patches.v0_3.seal_audit_ledger` (post-sync) seals TAX-046 events per tenant in creation order. A tenant that already has sealed entries is logged and left alone, so the verifier shows the gap rather than history being rewritten.

Alternatives and tradeoff:

- A separate ledger DocType copying every audit event: two sources of truth for the same action, and the TAX-046 case-version keys would have to be kept in step. Extending the existing DocType keeps one record per action.
- A per-entry signature or an external anchor (for example publishing the chain head): stronger against a database administrator who rewrites the whole chain consistently. It was left out of the prototype: the chain shows any partial edit, and `head_hash` from `verify_ledger` can be recorded outside the system when a deployment needs it.
- Automatic overrides when an officer's outcome differs from an agent draft: rejected. Counting disagreement with an AI suggestion as an "override" would push officers towards agent output. Only departures from named controls are overrides.
- Recording every Desk list view: out of scope. Desk read is supervisor-only, and the API reads are recorded.
