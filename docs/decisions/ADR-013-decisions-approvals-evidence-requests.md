# ADR-013: Officer decisions, approvals, evidence requests and their audit events

Status: proposed (TAX-046, pending review)
Owner and task: Leseli (owner, reassigned from Edga in #129), TAX-046; implemented by leseli-claude-20261104-046. Backend area review: Edga.
Date: 2026-11-04

(ADR-008 is reserved for TAX-033. ADR-012 is left for TAX-036, which is being implemented at the same time.)

Context and smallest prototype need: ADR-001 makes Frappe the holder of evidence requests and approved decision records, and Jube the case authority. It also says approval records precede idempotent calls into Jube, and a failed Jube call is a failed synchronisation, not an applied decision. ADR-007 left stale approvals, idempotent decision records and the Jube transition to this task. ADR-009 (TAX-034) gives `JubeCaseAdapter.transition`/`escalate`, which need the approved decision ID and a 1-5 rating. The contract (`requestEvidence`, `RequestEvidenceRequest`, `EvidenceRequest` in integration/api/openapi.json) needs an officer-authorised evidence request with `expected_version`. TAX-042 (decision UI), TAX-045 (evidence responses), TAX-047 (authenticated resume), TAX-057 and TAX-059 (audit ledger) build on this.

Decision:

- Three DocTypes. `Vati Decision` is one officer decision: outcome, rationale, cited evidence and findings, rating, the Jube status the officer saw, the proposer, the reviewer and the result of the one Jube operation. `Vati Evidence Request` is one authorised request (items, findings, due date, message, case version). `Vati Audit Event` is an append-only event for every proposal, review, request and Jube result: actor, role, action, subject, correlation ID, payload SHA-256 and outcome. All three carry `tenant_id`, `taxpayer_id` and `case_id`, so the TAX-029 wildcard hooks narrow them. Officers and services read; taxpayers get no DocPerm. Controllers refuse deletes, keep the proposal fields frozen, allow status to move only forward, and make audit events immutable.
- Outcomes come from a fixed allowlist, each mapped to one adapter call: `close_no_further_action` and `close_after_correction` resolve the case (`transition` to RESOLVED, which closes it in Jube); `request_further_evidence` moves it to AWAITING_EVIDENCE; `continue_investigation` moves it to INVESTIGATING; `escalate_to_supervisor` calls `escalate`. Any outcome that names an assessment, refund, payment, penalty, fraud or prosecution is refused as `prohibited_outcome`. There are no assessment or refund-payment methods. Closing outcomes must cite at least one evidence document or finding. Cited evidence must exist in the tenant and belong to the case's taxpayer.
- Separation of duties: auditors, specialists and supervisors propose; a different supervisor approves or rejects (`decision.approve` with `proposed_by`, ADR-007); only the proposer withdraws. A service identity can only record an agent draft (`draft.record`). A draft is never approved or executed (`agent_only_decision`). An officer can cite it (`draft_id`) in a proposal in their own words. The controller refuses a non-draft whose proposer role is not an officer role.
- Stale approvals are refused in three ways: (1) every proposal, review and evidence request takes the next case version, held in `Vati Audit Event.sequence_key` (unique on tenant, case and version), so an action on an older view gets `version_conflict` with `current_version`; (2) a proposal older than 72 hours cannot be approved; (3) the approver's call reads the case from Jube, and if its status differs from the status recorded at proposal the approval is refused.
- Duplicate outward actions: each mutation takes an `Idempotency-Key`, stored as a per-operation, per-tenant key plus a request digest (same key and request replays; different request is `idempotency_conflict`). A case has at most one open decision (`open_key`, unique), so two officers cannot queue competing actions. Approval runs the Jube call once; a retry (supervisor, or service identity through the new `decision.execute` action) only resends an approved decision whose last call failed with a retryable error and was approved less than 24 hours ago. The adapter sends nothing when Jube already holds the target, so a retry after a lost response does not apply twice. A `version_conflict` from Jube (the case moved) ends the decision as a non-retryable failure and frees the case for a new proposal.
- Execution order follows ADR-001: the approval and its audit event are written, then the adapter is called with the status the decision was approved against as `expected_status`, then the result (`synced` with Jube's reported status, or `failed` with code and retryability) and another audit event are written. Frappe stores only what Jube reported. It never sets a case status itself.
- The engine (`decisions/engine.py`) has no Frappe import. It works on a `Repository` port, implemented by `FrappeRepository` (store.py) and an in-memory version for tests. `CaseLifecycle` is the adapter's own method shape. The Frappe app cannot import `integration/jube`, so a site names a factory in `site_config.json` (`vati_case_lifecycle`). Without one, actions that need Jube fail as `upstream_unavailable` and nothing is recorded.
- Evidence requests record `status: recorded`. Moving the case to AWAITING_EVIDENCE is a separate approved decision, and delivery to the portal is TAX-045.

Alternatives and tradeoff:

- Approve and execute in two separate calls: clearer, but it leaves approved-and-unsent decisions waiting for a second click. One call plus an explicit retry keeps the approval and the attempt together, and the stored sync state shows a failure.
- Commit the approval before calling Jube (a separate transaction): stronger guarantee that the approval exists if the process dies mid-call. It was not done because Frappe request transactions and test isolation make in-request commits fragile. The adapter's replay safety covers the gap: a replayed approval finds Jube already in the target and records `changed: false`. TAX-033's outbox is the durable path for later.
- Use a Frappe document version as `expected_version`: Jube owns the case, and Frappe has no case row that changes, so the case version counts review actions in the audit trail instead.
- Store `authorised_by` as an officer UUID (contract type): no officer UUID mapping exists in Frappe yet. Views return the Frappe user. The Vati API layer must map it before exposing `EvidenceRequest`.
