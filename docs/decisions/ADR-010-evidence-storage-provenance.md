# ADR-010: Evidence storage, extraction revisions and provenance

Status: proposed (TAX-032, pending human review)
Owner and task: Edga (owner), TAX-032; implemented by keletso-claude-code on Keletso's instruction
Date: 2026-11-04

Context and smallest prototype need: ARCHITECTURE.md makes Frappe the holder of original evidence and its restricted reference; OpenAleph is a derived index. DATA_MODEL.md requires append-only evidence with a supersedes pointer, a document SHA-256, a page/record locator and an extraction version. The contract (`RegisterDocumentRequest`, `Evidence`, `EvidenceRef`, `EvidenceLocator` in integration/api/openapi.json) limits uploads to five media types and 25 MiB, and names a restricted Frappe File rather than a URL. TAX-038 (Docling), TAX-036 (OpenAleph) and TAX-043 (upload form) need one storage model to build on. (ADR-008 and ADR-009 were in use on open branches when this was written, so this ADR takes 010.)

Decision:

- Three `vati_tax` DocTypes. `Vati Evidence` is one immutable original: tenant, taxpayer, optional case and submission/request reference (Dynamic Link), version, supersedes pointer, lineage ID, server-computed SHA-256, media type, size and a link to its private File. `Vati Evidence Extraction` is one append-only extraction revision (status `success`/`partial`/`failure`, error code/category, extractor and version, page count, the SHA-256 of the evidence it read). Its `Vati Extraction Provenance` child rows hold each item's label, element ref, page, record locator, bounding box (l/t/r/b plus Docling `coord_origin`), optional field name, text and text SHA-256.
- Storage is a Frappe `File` with `is_private=1` (`/private/files/...`), renamed to the evidence UUID and attached to the evidence. The SHA-256 is computed from the bytes, then re-read from disk and compared, so a site setting that rewrites uploads (EXIF stripping) is refused instead of recording a wrong hash. Views never return the path or a URL.
- Uploads must have an allowed extension, leading bytes that identify an allowed type (PDF, PNG, JPEG, an OOXML workbook found by its ZIP central directory only, UTF-8 CSV), and a declared type, if given, that matches. Size is 1..26,214,400 bytes. Frappe's own PDF check (pypdf, JavaScript) also runs; a broken PDF is refused as `malformed_document`. Rejections use the ADR-003 `invalid_domain_input` code with a field reason.
- Append-only: controllers refuse every update and every delete. A correction is a new evidence version. A unique `supersede_key` (one successor per version) prevents a forked lineage. Same-content corrections are refused. Extraction revisions number 1..n per evidence under a unique `revision_key`, each pointing at the previous one. A `File` before_validate hook and a `File` has_permission hook stop an evidence file (and any File sharing its de-duplicated disk file) from being made public, moved, re-attached, edited or deleted.
- A failed extraction must carry an error code and no items. A partial one must carry an error code. A success must not. The contract projection maps success/partial to `completed` (partial keeps an error code, `partial_extraction` by default), failure to `failed`, and no revision to `pending`. Failure is never shown as an empty document.
- Isolation follows ADR-007. Both DocTypes carry `tenant_id` and `taxpayer_id`, so the wildcard hooks narrow them. DocPerms: officers and services read; a taxpayer reads only evidence it uploaded itself (`if_owner`) and no extraction revisions. A new `evidence.register` action (taxpayer for its own taxpayer; officers; services) authorises uploads. Recording an extraction needs `integration.callback` (service only). The evidence source is bound to the role, so a provenance label cannot be spoofed. Cross-tenant or cross-taxpayer references are reported as `not_found`.
- Upload and extraction recording are idempotent per tenant (unique `registration_key` plus a stored request digest). Same key and request replays; same key with a different request is `idempotency_conflict`. A case link also records a TAX-030 service link (`frappe`/`Vati Evidence`).

Alternatives and tradeoff:

- Store extracted text as a private JSON File instead of child rows: smaller DB rows, but the provenance could not be filtered or cited per item. Child rows are capped (5,000 items, 20,000 characters each, 2,000,000 per revision).
- Accept the caller's SHA-256: simpler, but it lets a client record a hash of different bytes. `register_file` only accepts a claimed hash after re-hashing the stored file.
- External object storage (S3/MinIO): better for scale and retention, but a second storage stack for the prototype. Frappe's `write_file` hook can move storage later without changing this model.
- Delete for operator resets: the demo resets by dropping a disposable site, so nothing needs a delete path. `Administrator` can still bypass via raw SQL, as with every Frappe record.

Official sources and version/date checked (2026-11-04): Frappe Framework v16.54.0 at the commit in `integration/frappe-framework.lock.json`. Source read in the pinned bench: `frappe/core/doctype/file/file.py` (private paths, content de-duplication, `handle_is_private_changed` moving the shared disk file, `has_permission` deferring to the attached document, pypdf JavaScript check), `frappe/core/api/file.py` (`get_max_file_size` default 25 MiB), `frappe/permissions.py` (`has_controller_permissions` with per-DocType and `*` hooks) and `frappe/model/document.py` (`before_validate` runs before `validate`). Docling notes in integration/docling/README.md (status `failure` returned with HTTP 200; `prov.page_no` plus `bbox`).

Verification performed: `python3 scripts/frappe_dev.py verify --project rsl-taxathon-frappe-tax019 --http-port 58010 --socketio-port 59010` on a disposable site: install, migrate twice, 47 site-backed tests passing (12 new in `vati_tax.evidence.test_evidence_bench` plus the TAX-029/030 suites) and 100 Frappe-free tests (14 new in `evidence/test_rules.py`). Removing the two File hooks made `test_evidence_and_its_file_are_immutable` fail. The site was dropped afterwards. No Docling call: extraction payloads are synthetic.

Consequences and revisit trigger: TAX-038 runs as the service identity, calls `store.record_extraction` with the bytes' SHA-256 and maps Docling `status` (`success`, `partial_success`, `failure`) to `success`/`partial`/`failure`. TAX-036 cites `extraction_view(...)["items"][i]["evidence_ref"]`. TAX-043 posts to `vati_tax.evidence.api.upload_evidence`. Revisit for real taxpayer data (retention, encryption at rest, malware scanning), for evidence larger than 25 MiB, or if extracted text must move out of the database.
