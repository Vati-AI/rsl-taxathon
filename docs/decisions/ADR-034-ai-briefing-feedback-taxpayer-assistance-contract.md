# ADR-034: Contract for AI briefings, provenance, finding feedback and taxpayer assistance

Status: proposed (TAX-096, pending review by Gupta (AI), Edga (backend), Leseli and Kananelo (frontends))
Owner and task: Keletso (integration), TAX-096; implemented by keletso-claude-20261105-096.
Date: 2026-11-05

Context and smallest prototype need: ADR-031 approved routed models, required provenance on every AI output and set two permission contexts. In the officer context, investigation agents act for an officer. In the taxpayer context, an assistant acts for one taxpayer and never sees risk scores, internal notes, findings or other taxpayers. ADR-021 said exposing briefings "needs a contract change and review". Before this ADR, the Vati contract (ADR-003) had no briefing, provenance, finding feedback or taxpayer-facing AI operations. Without one, TAX-086, TAX-090, TAX-093, TAX-098, TAX-099, TAX-100 and TAX-101 would each invent a different shape. ADR-003 and ADR-031 already settle the request rules and the model architecture. This ADR records only the choices they leave open.

Decision:

- **Provenance versus disclosure.** `AnalysisProvenance` mirrors the TAX-089 router record (`ai/models/router.py`, `ROUTER_VERSION tax089-router-v1`). It keeps the fields ADR-031 names, plus `attempts`, `configured_model_id`, `task` and `router_version`. The router's `rate_limit` headers and configuration `notes` stay out, because they are operational logs, not review data. `AiDisclosure` is the small, UI-ready subset: source (`hosted_model`, `local_model`, `template` or `mock_fixture`), provider, model ID, `fell_back` and `advisory_only: true`. Officers get both. Taxpayers get only the disclosure, which is enough for TAX-101's "model or template" label and reveals nothing internal. Where a record carries both, `check_example` requires them to agree.
- **Additive changes to existing schemas.** `Finding.analysis_provenance` and `Finding.feedback_summary` are optional, and so is `InvestigationRun.analysis_provenance`. This keeps existing producers, fixtures and the auditor client valid (API_STANDARD prefers additive optional fields). On `CaseBriefing`, provenance is required, because every briefing has a producer, even if it is the template.
- **Briefing read.** `getCaseBriefing` projects ADR-021's `briefing_record`, statement for statement and reference for reference, so TAX-090 maps it without reinterpreting anything. It adds `case_version`, `disclosure` and a `checkpoint` block that projects the TAX-047 interrupt (`action_id`, `kind`, `case_version`, `payload_digest`, `proposed_by`, `last_rejection`). The always-null conclusion fields stay in, as structural guarantees.
- **Finding feedback** is an append-only record, not a state update, so it takes no `expected_version`. Feedback never changes the finding (`changes_finding: false`). A stale case version would only block an opinion, never prevent a wrong change. The actor and role come from the session. A body that names an actor is refused (400), because the schema is closed. A newer feedback by the same officer links `previous_feedback_id`. Each feedback snapshots the judged finding's producer and provenance, so the TAX-070 loop knows which model or prompt was judged. Officer-authored findings take no feedback. Feedback is not an approval: decisions still need TAX-046 proposal and review by different officers.
- **Taxpayer assistance routes** sit under `/api/v1/taxpayers/{taxpayer_id}/assistance/` and are marked `x-vati-audience: taxpayer`. The path names the taxpayer, so scoping can be checked: another taxpayer's ID is 404 (the same as missing, as the TAX-045 portal does), and officers or services get 403. The client never supplies validation results. The server recomputes them from the stored draft submission.
- **Structural exclusion.** Taxpayer operations reference only `TaxpayerFacing*` schemas and a fixed list of shared primitives. Every object is closed, and officer-only field names are refused. `contract.lint_spec` enforces all of this, and `check_example` repeats the field scan on examples. Names alone can't stop a server copying internal data into an allowed text field. That stays a runtime test for TAX-100 and TAX-102.
- **Synchronous assistance with a finite budget, not a job.** API_STANDARD asks AI work to use asynchronous jobs with a deadline. The taxpayer explanation, document review and draft operations instead answer synchronously within a 25-second server budget. Inside that budget, the ADR-031 fallback chain ends at the deterministic template, which always answers, so a timeout gives a disclosed template result instead of a hung request. They are POST operations with `Idempotency-Key`: the result and its provenance are stored, and a replay returns them without another model call. Officer briefings come from investigation runs, which stay asynchronous (`startInvestigation`, 202).
- **Draft, then explicit confirmation.** `draftEvidenceResponse` stores a draft (`status: draft`, `sent_to_rsl: false`). Only `confirmEvidenceResponseDraft` sends anything. It needs `declaration: true` and `expected_version`, takes the taxpayer's final, possibly edited answers and records the TAX-045 evidence response. A same-key retry replays the confirmation. A second confirmation with a new key is `409 version_conflict`, so there is never a second response.
- No new error codes. Refusal reasons go in `field_errors[].code`, as in ADR-018: `reason_required`, `modified_text_required`, `modified_text_not_allowed`, `officer_finding`, `submission_not_editable`, `request_closed`.

Alternatives and tradeoff:

- **Full provenance for taxpayers.** It is more transparent, but it exposes prompt versions, attempts and token use that a taxpayer cannot act on, and it would put an officer-side schema in the taxpayer closure. Rejected in favour of the disclosure subset.
- **Session-derived taxpayer routes (`/api/v1/assistance/...`).** The URL is shorter, but responses can't be checked against an explicit scope, and service principals acting for a taxpayer would need a hidden parameter. Rejected.
- **GET for explanations and document review.** It is the natural verb for reads, but each call costs model tokens and its stored result needs an idempotency key, so it was rejected. Only reading a stored draft is a GET.
- **Async jobs for taxpayer assistance.** This follows API_STANDARD literally, but the portal would need polling for a 1–3 second fast-role call, and the template fallback already bounds latency. Rejected for v1. Revisit if the 25-second budget can't be met.
- **`expected_version` on feedback.** It is consistent with other case mutations, but it would refuse valid opinions whenever any other case action bumped the version. Rejected.

Verification performed: `python3 integration/api/contract.py` lints the contract and validates 45 HTTP examples (19 new: 7 success, 12 error or replay) and 2 events. `python3 -m unittest discover -s tests/contracts` runs 113 tests, including 29 in `test_ai_assistance_contract.py`. These cover internal fields and officer schemas being refused in taxpayer schemas and responses, open objects, route and audience mismatch, cross-taxpayer and cross-tenant responses, draft and confirmation idempotency, stale confirmation, missing declaration, feedback replay and conflict, actor-in-body, briefing conclusions, references and next actions, disclosure-provenance agreement, and provenance enums and float settings. No server implements these operations yet.

Consequences and revisit trigger: TAX-086 stores provenance and feedback in these shapes. TAX-090 serves `getCaseBriefing` and `recordFindingFeedback`, and TAX-100 serves the taxpayer operations, both reusing the examples as contract tests. TAX-093 and TAX-101 render `AiDisclosure`. TAX-098 and TAX-099 produce the taxpayer-facing results. The TAX-029 policy needs a `finding.feedback` action (auditor, specialist, supervisor) and a taxpayer assistant action (own taxpayer); TAX-086 and TAX-100 add them. Revisit if the router's provenance record changes, if the 25-second budget is not met in TAX-100, if officers need free-text quotes in briefings (ADR-021), or if a taxpayer-facing field is needed that the exclusion lint refuses. In that case, rename it or extend the lint with a test, never bypass it.
