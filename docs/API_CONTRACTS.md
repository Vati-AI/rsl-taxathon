# API and fixture contract

Production route names below are proposed Vati routes to implement in TAX-018. They are not claims about upstream APIs.

- POST /cases; GET /cases/{case_id}; POST /cases/{case_id}/investigate
- GET /cases/{case_id}/evidence, /entities, /findings
- POST /cases/{case_id}/documents; POST /cases/{case_id}/request-evidence
- Frappe portal submissions and responses map to these services through authenticated server calls.

Every request resolves tenant/user permissions; case IDs alone never authorize access. Every mutation carries idempotency key and expected version. Event envelope: schema_version, event_id, tenant_id, case_id, correlation_id, type, occurred_at, idempotency_key, payload. Monetary values are decimal strings with currency.

Findings distinguish facts, inference, missing/unverified/contradictory evidence, legal-route verification and proposed action. Evidence references include source record/document SHA-256 and page/record locator. Errors identify service, retryable code and correlation ID without leaking document content or credentials.

## Executable fixture interface

`python3 scripts/dev.py serve` exposes GET /api/health, /api/scenarios and /api/cases on localhost:58080. Each returns `mode: fixture` and `synthetic: true`. GET /api/cases/{id} retrieves a fixture or 404. It has no mutations, authentication or live-service fallback. Use it for UI development only. `/auditor/` and `/taxpayer/` show starter interfaces; they are not completed product flows.

The same server also serves the contract-shaped `listCases`, `getCase` and `getTaxpayer` operations (TAX-040) and `listEvidence` and `listEntities` (TAX-041) under `/api/v1` from synthetic fixtures, applying the contract's tenant and request rules (see integration/api/README.md). The auditor app uses these. The officer review operations (`getCaseReview`, `listFindings`, `proposeDecision`, `reviewDecision`, `requestEvidence`; TAX-042) are served too and accept POST; their changes are in-memory fixture state only, reset when the server restarts. `listFindings` is the one source of findings; its citations name evidence served by `listEvidence`. The supervisor-only `getManagementSummary` (TAX-060, ADR-020) is measured from synthetic records.

## AI briefing, provenance, feedback and taxpayer assistance (TAX-096)

[ADR-034](decisions/ADR-034-ai-briefing-feedback-taxpayer-assistance-contract.md) records the choices; ADR-031 (models, two permission contexts) and ADR-021 (validated briefings) are unchanged. These operations are contract only. The fixture server answers them with 404 until TAX-090 (officer side) and TAX-100 (taxpayer side) implement them.

- **`AnalysisProvenance`** records how an AI output was produced: `provider` (`mock`, `groq`, `gemini`, `ollama` or `template`), `model_id` (the model actually used) and `configured_model_id`, `role` (`reasoning`, `fast` or `document`), router `task`, `prompt_version` and `settings`. It also records `fallback_level` and `fallback_level_name` (`mock`, `hosted`, `local` or `template`), `fell_back`, every `attempts` entry with its outcome, `latency_ms`, `token_usage` and `validation` (`passed`, `failed` or `not_run`, plus a reason). It mirrors the TAX-089 router record. Settings are scalars, and a fractional temperature is a decimal string. Findings (`analysis_provenance`, optional, null for rule and officer findings), investigation runs (one entry per model call) and briefings (required) carry it. Officers see it; taxpayers never do.
- **`AiDisclosure`** is what a UI shows next to any AI item. `source` is `hosted_model`, `local_model`, `template` or `mock_fixture`, alongside `provider`, `model_id`, `fell_back` and `advisory_only: true`. Where a record has both, the checker requires the disclosure to match the provenance.
- **`getCaseBriefing`** (`GET /api/v1/cases/{case_id}/briefing`, optional `run_id`) is for officers only. It returns the ADR-021 briefing recorded once per run: five `sections` of `BriefingStatement`s. Each statement cites an evidence citation with an `EvidenceRef`, a run search or an in-scope document. It also returns `rejected_statements` with reason codes, `searches`, `search_digest`, provenance, disclosure and `checkpoint` (run status, `awaiting_human`, the pending TAX-047 interrupt with its action digest). `decision`, `legal_conclusion` and `enforcement_conclusion` are always null, and `requires_officer_approval` is always true. A case with no briefing returns 404.
- **`recordFindingFeedback`** (`POST /api/v1/cases/{case_id}/findings/{finding_id}/feedback`) is for an auditor, specialist or supervisor. The body is `verdict` (`accepted`, `modified` or `rejected`), `reason_code`, `reason` (required for modified and rejected) and `modified_explanation` (only for modified). The actor and role come from the session, and an actor in the body is a 400. Feedback is append-only: a newer feedback by the same officer links `previous_feedback_id`. It snapshots the judged finding's producer and provenance for the TAX-070 loop. `changes_finding` is always false, so feedback never edits a finding, case or decision and is not an approval. A replay with the same `Idempotency-Key` returns the stored feedback, and a changed body is `422 idempotency_conflict`. `Finding.feedback_summary` gives the counts and the viewer's own latest verdict.
- **Taxpayer assistance** (`/api/v1/taxpayers/{taxpayer_id}/assistance/...`, `x-vati-audience: taxpayer`) is for the taxpayer named in the path only. Another taxpayer's ID returns 404, the same as a missing one. Officers and services get 403.
  - `explainValidationResults` recomputes the deterministic pre-submission result of the taxpayer's own draft submission. It returns that result unchanged next to plain-language explanations with steps.
  - `reviewSubmissionDocuments` returns extracted fields to confirm (extracted value, declared value, locator, reason) and flagged invoice rows.
  - `draftEvidenceResponse` saves a draft answer to one of the taxpayer's own evidence requests. Each item is `matched`, `partially_matched` or `missing`, and only the taxpayer's own documents are cited.
  - `getEvidenceResponseDraft` reads a draft.
  - `confirmEvidenceResponseDraft` is the only step that sends anything. It needs `declaration: true` and `expected_version`, takes the taxpayer's final edited answers, and records the TAX-045 response. A replay returns the confirmation, and a second confirmation is `409 version_conflict`.

  Assistance results and drafts are stored with their provenance, and a same-key replay returns them without a model call. Model calls run within a 25-second budget and fall back to the template. Explanations and drafts never change declared figures or submit (`changes_declared_figures: false`, `requires_taxpayer_confirmation: true`, `sent_to_rsl` false until confirmation).
- **Taxpayer exclusion is structural.** Taxpayer operations use only `TaxpayerFacing*` schemas plus the primitives `Uuid`, `Timestamp`, `Sha256`, `Money`, `EvidenceLocator`, `DocumentType`, `AiDisclosure` and `ModelProvider`. Every object is closed (`additionalProperties: false`). `contract.lint_spec` fails if a taxpayer operation references any other schema, has an open object, or has a field named like `case_id`, `findings`, `confidence`, `legal_route`, `analysis_provenance` or `notes`, or containing `risk`, `score`, `finding`, `internal`, `officer`, `lane`, `jube` or `audit`. `check_example` also scans taxpayer responses for those names and checks `taxpayer_id` against the path. `tests/contracts/test_ai_assistance_contract.py` holds the negative tests.

The versioned contract is [integration/api/openapi.json](../integration/api/openapi.json) with synthetic examples and a dependency-free checker; see [integration/api/README.md](../integration/api/README.md) and [ADR-003](decisions/ADR-003-vati-api-contract.md). Real adapter contracts follow in the service tasks. Tests must verify denied access, duplicate mutations, stale state, missing evidence and upstream timeout in addition to success.
