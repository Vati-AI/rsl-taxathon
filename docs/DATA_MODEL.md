# Canonical data model (implementation contract)

Use UUIDs for internal IDs, UTC ISO timestamps, explicit tenant IDs and string decimal amounts with ISO currency. Never use floats for money. Keep source IDs separately; never join entities solely on names.

| Entity | Key fields and relationships |
|---|---|
| Tenant / UserMembership | tenant_id, user_id, role (taxpayer, auditor, specialist, supervisor, service), taxpayer_id for taxpayer members (TAX-029) |
| Taxpayer | taxpayer_id, tenant_id, synthetic/approved tax identifier, legal name, industry |
| Submission | submission_id, taxpayer_id, period, type, status, source_ref, version |
| VATReturn / RefundClaim | submission_id, declared amounts, currency, period, claim_id |
| Invoice / Payment / Import | record_id, taxpayer_id, counterparty_id, date, currency, decimal amounts, source_ref |
| RelatedParty | source_entity_id, target_entity_id, relationship_type, valid dates, evidence_ids |
| Evidence | evidence_id, tenant_id, case_id, document_sha256, restricted object_ref, page/record locator, extraction version, source, received_at |
| Case | case_id, tenant_id, taxpayer_id, submission_id, status, assigned_officer, version |
| Finding | finding_id, case_id, category, rule/model version, explanation, evidence_ids, unresolved_amount, confidence, evidence_gap |
| EntityMatch | match_id, local_entity_id, candidate_id, score, dataset/version, reviewer, resolution |
| InvestigationRun | run_id, case_id, workflow_version, checkpoint/thread_id, status, tool_calls, evidence_ids |
| EvidenceRequest / Response | request_id, case_id, requested items, approval_actor, sent_at, response_refs |
| Decision | decision_id, case_id, authorized_actor, outcome, rationale, evidence_ids, decided_at |
| AuditEvent / Outbox | event_id, tenant_id, case_id, actor, action, timestamp, correlation_id, payload_hash, delivery status |

Proposed UI state projection (map to configured Jube workflow; do not create a second lifecycle): RECEIVED → VALIDATING → INVESTIGATING → AWAITING_HUMAN → RESOLVED. AWAITING_EVIDENCE and FAILED_PROCESSING are explicit branches with retry/re-entry rules. Only authorized humans can transition AWAITING_HUMAN to RESOLVED. Closure does not authorize refund payment or enforcement.

TAX-033 implements the outbox as the `Vati Outbox Event`, `Vati Outbox Attempt` and `Vati Outbox Effect` DocTypes ([ADR-008](decisions/ADR-008-durable-outbox.md)).
TAX-031 implements Taxpayer, Submission, VATReturn, RefundClaim and imported services as `Vati Taxpayer`, `Vati Submission`, `Vati VAT Return`, `Vati Refund Claim` and `Vati Imported Service` (LSL Currency columns with strict decimal parsing, `YYYY-MM` or `YYYY-Qn` periods; [ADR-010](decisions/ADR-010-submission-doctypes.md)).
TAX-039 adds `Vati Case Sync` (staff-only mirror of one Jube case: Jube case number, projected status, escalation, closure and the `observed_at` watermark) and `Vati Bridge Inbound Event` (replay ledger for posted case-state envelopes). `Vati Submission` gains the server-owned `review_status` and `review_status_at`, the only Jube-derived fields a taxpayer can read ([ADR-028](decisions/ADR-028-frappe-jube-submission-bridge.md)).

TAX-087 adds `Vati Entity Index` (ledger of FtM entities written to the tenant's OpenAleph collection: entity ID, schema, digest, the case and outbox event that first wrote it, and a `reindex_required` flag when a later mapping differs) and `Vati Screening Result` (yente candidates, as unreviewed contract `MatchCandidate` objects, for one case party on one dataset version). Both are staff-read, written only by `vati_tax.pipeline`, and keyed so a replay writes nothing twice ([ADR-037](decisions/ADR-037-event-wiring-frappe-services.md)).

Maintain a `service_links` table unique on (tenant_id, service, external_id), mapping case_id/evidence_id to Jube/OpenAleph/Frappe IDs. Frappe document names are namespaced by DocType. TAX-030 implements this as the `Vati Service Link` DocType ([ADR-006](decisions/ADR-006-canonical-ids-service-links.md)). Optimistic version checks prevent concurrent decision overwrites. Idempotency key and request digest prevent replay with changed payloads. Foreign keys include tenant boundaries or equivalent database constraints.

Evidence is append-only: corrections create a new version with a supersedes pointer. TAX-032 implements this as `Vati Evidence` (immutable original, server-computed SHA-256, private File) and `Vati Evidence Extraction` (append-only revisions with page/bbox provenance) ([ADR-011](decisions/ADR-011-evidence-storage-provenance.md)). TAX-046 implements EvidenceRequest, Decision and AuditEvent as `Vati Evidence Request`, `Vati Decision` and `Vati Audit Event`. A decision is proposed by an officer, approved by a different supervisor, and runs one Jube operation; the case version counts review actions in the audit trail ([ADR-013](decisions/ADR-013-decisions-approvals-evidence-requests.md)). TAX-059 makes `Vati Audit Event` the tenant audit ledger: every entry (decision events, reads, overrides, refused attempts) has a category and a place in a per-tenant SHA-256 hash chain, so edits, gaps and reordering are detectable ([ADR-015](decisions/ADR-015-audit-ledger-separation-of-duties.md)). TAX-045 adds `Vati Evidence Response`: one immutable taxpayer response per evidence request, answering each requested item by index with the taxpayer's own evidence IDs or a reason; sending it moves the request to `responded` ([ADR-019](decisions/ADR-019-evidence-request-responses.md)). TAX-044 extends `Vati Refund Claim` with the period's declared output and input VAT, a `Vati Refund Claim Invoice` child table (the taxpayer's purchase-invoice schedule: number, date, supplier, amounts excluding VAT, VAT and total, amount paid, invoice and contract documents) and server-computed schedule totals ([ADR-023](decisions/ADR-023-presubmission-reconciliation.md)). TAX-078 adds `Vati Correction Reminder`: a taxpayer-facing reminder recorded by staff from an approved decision that recorded an omission. It has a topic mapped to TAX-044 prompt codes, a versioned explanation with its change history, and an `active`/`withdrawn` status. It is hidden while its decision is challenged or after it was overturned ([ADR-032](decisions/ADR-032-correction-reminders.md)). Findings distinguish observed facts, inference, missing evidence and proposed actions. Store reviewed outcomes separately from model suggestions. A legal-route field remains `unverified` until a qualified reviewer supplies an authoritative citation.

TAX-074 derives a per-(tenant, case) scheme, ownership and intermediary graph from the FtM entities. Legal, beneficial, director, adviser and intermediary links are separate edge types, each backed by one source record and its evidence. Conflicting records stay separate, and nothing carries a risk label ([ADR-026](decisions/ADR-026-scheme-ownership-intermediary-graph.md)).

TAX-079 defines offline adapter contracts for supplied bank-statement, mobile-money, foreign-payment and digital-wallet files (`integration/payment_channels`). Each line becomes an immutable `payment_channel_record.v1`. It carries a lawful-access permission (basis, approval reference, requester/approver, scope, expiry) and provenance (channel, synthetic provider, evidence ID and SHA-256, retrieval method, received time, adapter version). Lines map to FtM `Payment`. Payment method never produces a label or signal. Live connectors are out of scope ([ADR-027](decisions/ADR-027-lawful-payment-channel-contracts.md)).

TAX-086 implements Finding as `Vati Case Finding` and officer finding feedback as `Vati Finding Feedback` ([ADR-041](decisions/ADR-041-case-findings-record.md)). A finding is one append-only record from a TAX-035 Jube rule (`jube_rule`), a LangGraph playbook run (`langgraph_run`) or an officer. It carries `tenant_id` and `case_id` but no `taxpayer_id`, and it records kind, category, code, explanation, `EvidenceRef`s (evidence ID, stored document SHA-256, source-record locator), the unresolved amount as a decimal string with its currency, confidence, alternatives, an `unverified` legal route and a proposed action that needs human approval. It also names its producer version and the rule (rule, ruleset, input digest) or playbook registry stamp and run. Agent findings must carry their TAX-096 `AnalysisProvenance`; rule and officer findings carry none. A changed result is a new revision that supersedes the previous one, and replaying the same idempotency key writes nothing. Feedback is an append-only verdict (accepted, modified or rejected, with a reason code and reason) by the session officer. It links that officer's previous feedback and snapshots the judged finding's producer and provenance for the TAX-070 loop. It never changes the finding.

Framework update (ADR-040), implemented as pure contracts and tools in TAX-111 to TAX-116 (no Frappe DocTypes yet): `RslSourceRecord` references for e-Tax, IDMS, Online Refunds Application, RSL fraud score and ASYCUDA, carrying source system, record ID, contract version and retrieved_at, never a second copy of the source store (TAX-111). `InputVatMatch` per claimed line, classified matched, supplier_gap, unintegrated_supplier or unmatched (TAX-112). `SourceLedger` (SAF-T-style GL, supplier/customer ledger and payment lines, original file hashed), `RecomputeReport` (declared, recomputed and difference per line with source record IDs) and a per-record quality of complete, verified, unverified or contradicted (TAX-113). A lane proposal gains a proposed service target and due date, and an advisory `undisputed_amount` (TAX-114). `ForeignPaymentMatch` per counterparty and period, with money out, booked and declared amounts and the tolerance used (TAX-115). TAX-116 adds the candidate rule register and policy-gap register (`ai/workflows/rule_register*.json`, `policy_gap_register.json`), all `unverified`. TAX-118 measures them on a sealed synthetic population ([results](evidence/TAX-118/RESULTS.md)).

TAX-121 runs those checks inside the pipeline ([ADR-042](decisions/ADR-042-assurance-checks-in-the-pipeline.md)). A sent refund claim enqueues `assurance.requested` before `case.registered`. Results are recorded as `Vati Case Finding`s with producer `vati_check`, which name the check in `rule` and carry `source_refs` (`RslSourceRef`: system, record ID, contract, record SHA-256, line) and the TAX-116 `candidate_route` (never eligible for assessment; the legal route stays `unverified`, or `no_verified_route` for a policy gap). `Vati Lane Proposal` is an append-only per-claim TAX-114 lane: lane, reasons, service target and due date, claimed, undisputed and disputed amounts, inputs and line matches; changed inputs add a superseding revision. `Vati Assurance Run` keeps one record per event: status (`completed`, `degraded`, `not_run`, `superseded`), per-check status, which services were live, recorded or unavailable, and counts. The taxpayer's own records are one CSV `Vati Evidence` document referencing the `Vati Taxpayer`; RSL records are read through the site's recorded TAX-111 fixture (`vati_rsl_sources`) and only referenced.

Jube is operational Case authority. Frappe implements users, tax submissions, requests and approved decision records. Vati stores cross-service links and delivery state. See ADR-001.
