# Frappe custom app

This is an installable package skeleton, not a configured site or complete DocType model. TAX-019 installs it in an isolated bench; TAX-029 adds roles and tenant permissions. Do not load it into existing HR/helpdesk/production sites.

Install and verify it with the repository tooling, never by hand on a shared site:

```sh
python3 scripts/frappe_dev.py init     # pinned Frappe v16.54.0 bench, taxathon.localhost site, editable vati_tax
python3 scripts/frappe_dev.py verify   # new disposable site: install, migrate twice, import, app tests, drop
```

See [docs/FRAPPE_DEV.md](../../docs/FRAPPE_DEV.md) for running a second checkout with its own project/ports.

Package layout:

- `vati_tax/hooks.py` declares the app; `modules.txt` declares the `Vati Tax` module (package `vati_tax/vati_tax`), where DocTypes go.
- `vati_tax/patches.txt` uses Frappe's `[pre_model_sync]` / `[post_model_sync]` sections. Add a dotted path plus a test for every data migration; never edit site databases manually.
- `pyproject.toml` ships `*.txt`, JSON, HTML and `public/` assets with the package.
- `vati_tax/api.py` exposes only an authenticated scaffold health method. `vati_tax/portal` holds the TAX-021 taxpayer portal boundary and its Frappe-free unit tests. TAX-043 adds `portal/claims.py` (pure VAT refund claim form rules) and `portal.api.submit_refund_claim`, which stores a refund claim in the TAX-031 DocTypes in one transaction with idempotent replay; site-backed tests are in `portal/test_refund_claim_bench.py`.
- TAX-044: `submissions/invoices.py` holds the pure purchase-invoice schedule rules used by `Vati Refund Claim` (now with period figures, a `Vati Refund Claim Invoice` child table and server totals) and by the portal. `portal/presubmission.py` is the only module that imports from `ai`: it runs the unchanged TAX-048 `ai.tools.refund_reconciliation` (mounted read-only in the dev stack, no AI dependencies installed) and returns allowlisted figures and prompts through `portal.api.review_refund_claim` ([ADR-023](../../docs/decisions/ADR-023-presubmission-reconciliation.md)).
- `vati_tax/responses` (TAX-045) holds taxpayer responses to evidence requests: `rules.py` (pure taxpayer view allowlist, status mapping and answer rules), `store.py` (scoped reads, the immutable `Vati Evidence Response` and the `responded` transition with a ledger entry). The portal methods are in `portal/api.py` ([ADR-019](../../docs/decisions/ADR-019-evidence-request-responses.md)).
- `vati_tax/identity` (TAX-029) holds roles, tenant memberships, service identities and permissions: `policy.py` (pure rules and the role/action matrix), `permissions.py` (Frappe hooks, `require_action`), `provision.py` (operator helpers) and the `Vati Tenant` / `Vati Tenant Membership` DocTypes. Any DocType in this app with a `tenant_id` field (plus `taxpayer_id` for taxpayer-owned records) is tenant-isolated automatically; see [docs/PERMISSIONS.md](../../docs/PERMISSIONS.md).
- `vati_tax/ids` (TAX-030) holds canonical case IDs and service links. `canonical.py` has the pure rules, `mapping.py` the internal persistence API (`register_case`, `record_link`, `apply_link_event`, `resolve_case`, `case_service_links`), and the `Vati Case Identity` / `Vati Service Link` DocTypes store them ([ADR-006](../../docs/decisions/ADR-006-canonical-ids-service-links.md)).

- `vati_tax/outbox` (TAX-033) holds the durable outbox ([ADR-008](../../docs/decisions/ADR-008-durable-outbox.md)). `policy.py` has the pure rules, `store.enqueue` writes an event in the caller's transaction, `worker.dispatch` delivers committed events at least once (with leases, bounded backoff, dead letters and per-case order), and `api.py` provides operator retry and effect reconciliation. Register handlers with `vati_outbox_handlers = {"<event type>": "dotted.path"}` in hooks. Route outward calls through `Delivery.effect` so that replays never duplicate them.
- `vati_tax/evidence` (TAX-032) holds evidence storage, extraction revisions and provenance. `rules.py` has the pure upload/extraction rules, `store.py` the internal API (`register_upload`, `register_file`, `record_extraction`, `get_evidence`, `evidence_history`, `list_extractions`, `case_evidence`, `verify_integrity`) and `api.py` the whitelisted `upload_evidence`/`get_evidence` methods. The `Vati Evidence`, `Vati Evidence Extraction` and `Vati Extraction Provenance` DocTypes store them ([ADR-011](../../docs/decisions/ADR-011-evidence-storage-provenance.md)).

- `vati_tax/decisions` (TAX-046) holds officer decisions, approvals, evidence requests and their audit events. `rules.py` has the pure input rules and outcome allowlist, `engine.py` the Frappe-free workflow (propose, approve/reject/withdraw, one Jube operation per approved decision, retry, evidence requests), `store.py` the Frappe repository and `api.py` the whitelisted methods. The `Vati Decision`, `Vati Evidence Request` and `Vati Audit Event` DocTypes store them ([ADR-013](../../docs/decisions/ADR-013-decisions-approvals-evidence-requests.md)). A site names its Jube adapter factory in `site_config.json` as `vati_case_lifecycle`.
- `vati_tax/audit` (TAX-059) seals every `Vati Audit Event` into a per-tenant hash chain and records reads, overrides and refused attempts. `ledger.py` has the Frappe-free chain, verifier, review-only signals and summary, `service.py` the policy-checked operations, `store.py` the Frappe binding and `api.py` the supervisor-only whitelisted methods ([ADR-015](../../docs/decisions/ADR-015-audit-ledger-separation-of-duties.md)).
- `vati_tax/bridge` (TAX-039) connects a sent submission to Jube and mirrors Jube's case state back. A taxpayer's send registers the case and enqueues one `case.registered` outbox event. The handler invokes the risk model with the declared figures and asks the TAX-034 adapter for the case. Observations of Jube state (from the handler, a five-minute poller, or a service identity posting `case.status_projected` to `api.receive_case_status`) update the staff-only `Vati Case Sync` and the submission's taxpayer-facing `review_status`. `rules.py` has the pure rules (status mapping, payload allowlist, replay, ordering, loop guard), `store.py` the Frappe binding and `api.py` the whitelisted methods ([ADR-028](../../docs/decisions/ADR-028-frappe-jube-submission-bridge.md)). A site names its risk factory in `site_config.json` as `vati_risk_evaluator` (and the shared `vati_case_lifecycle`).
- `vati_tax/integrations` (TAX-085) builds the `integration/` service adapters from the `vati_services` site config that `scripts/frappe_dev.py init` writes from ignored local files ([ADR-035](../../docs/decisions/ADR-035-service-adapters-in-frappe.md)). `config.py` is the Frappe-free builder, `factories.py` the site factories (`case_lifecycle` for `vati_case_lifecycle`, `risk_evaluator` for `vati_risk_evaluator`, plus `docling_extraction`, `openaleph_ingest` and `yente_matcher`), and `live_check.py` the verify-site-only live Jube proof. A missing service is `upstream_unavailable` (`<service>_not_configured`).
- `vati_tax/pipeline` (TAX-087) wires a sent claim and its evidence through the services ([ADR-037](../../docs/decisions/ADR-037-event-wiring-frappe-services.md)). After the TAX-039 bridge registers the case, the claim's documents are linked to it and each gets an `evidence.received` outbox event (so does any evidence linked to a case later). Its handler converts the original with Docling and records the extraction; `extraction.completed`/`extraction.failed` then maps the case to FtM entities, writes new ones to OpenAleph (`Vati Entity Index`) and screens the parties with yente (`Vati Screening Result`). `rules.py` has the pure rules, `store.py` the Frappe binding, `api.case_status` the operator view (System Manager), `fakes.py` the transports used by the bench tests and `demo.run` (verify sites only: sends SYN-001 and SYN-002 end to end). The handlers run as the site's `vati_pipeline_service_user`.
- `vati_tax/findings` (TAX-086) records per-case findings from TAX-035 rule signals, TAX-049 related-party playbook results and officers, plus append-only officer feedback on them. `rules.py` holds the pure contract rules and the producer translators, `engine.py` the Frappe-free workflow (idempotent recording with superseding revisions, reads, feedback, the TAX-070 feedback reader), and `store.py` the Frappe binding the pipeline and TAX-090 call. The `Vati Case Finding` and `Vati Finding Feedback` DocTypes store them ([ADR-041](../../docs/decisions/ADR-041-case-findings-record.md)).
- `vati_tax/exports` (TAX-062) handles scoped evidence export requests, a different supervisor's authorisation, the frozen hash/provenance manifest and retention metadata. `rules.py` has the pure request, manifest and retention rules, `service.py` the Frappe-free workflow (every step and refusal goes to the audit ledger), `store.py` the Frappe binding and `api.py` the whitelisted methods. The `Vati Evidence Export` DocType stores the requests. Retention periods come from `vati_retention_days` in `site_config.json` and are unverified placeholders; nothing is deleted ([ADR-016](../../docs/decisions/ADR-016-evidence-export-retention.md)).
- `vati_tax/workflows` (TAX-065) is the human gate for TAX-064 learned workflows. A proposal is recorded as a version, a supervisor who did not record it approves or rejects it (`playbook.approve`), a supervisor activates it, and every activation is appended with a rollback reference. Rollback restores the previous approved version, and only the version in force passes `check_workflow_execution`. `rules.py`/`service.py` are Frappe-free, `store.py` binds them to the `Vati Workflow Version` and `Vati Workflow Activation` DocTypes and `api.py` has the whitelisted methods ([ADR-025](../../docs/decisions/ADR-025-learned-workflow-approval-rollback.md)).
- `vati_tax/challenges` (TAX-069) links an approved decision to an objection, an appeal and their reviewed outcomes. `rules.py` has the pure rules, outcome list and decision digest, `service.py` the Frappe-free workflow (lodge, review by an uninvolved supervisor, history), `store.py` the Frappe binding and `api.py` the whitelisted methods. The `Vati Decision Challenge` DocType stores them. Decisions and evidence are never rewritten, and an overturned outcome raises a review-only `decision_overturned` signal ([ADR-024](../../docs/decisions/ADR-024-objections-appeals-final-outcomes.md)).
- `vati_tax/reminders` (TAX-078) holds correction reminders from reviewed omissions in a taxpayer's earlier claims. `rules.py` has the topics (each mapped to TAX-044 prompt codes), the taxpayer view allowlist and the source-decision check, `service.py` the Frappe-free workflow (record, correct or withdraw with a reason, staff history, the portal list), `store.py` the Frappe binding and `api.py` the staff methods. The `Vati Correction Reminder` DocType stores them; the portal reads them through `portal/api.py` ([ADR-032](../../docs/decisions/ADR-032-correction-reminders.md)).

- `vati_tax/rsl_referrals` (TAX-123) takes in audit referrals from RSL's risk-based audit system through the assumed contract `rsl.audit_system.referral.v0-assumed` ([ADR-047](../../docs/decisions/ADR-047-rsl-audit-referrals.md)). `rules.py` is Frappe-free (plan, replay, RSL-owned inputs), `store.py` opens one case per RSL audit case reference and records the append-only `Vati RSL Referral` (RSL's reference, record hash and RSL-owned risk-set scores), and `api.py` has the operator-only intake and the officer read.
- `vati_tax/rsl_outbound` (TAX-124) sends officer-approved results back to RSL through the assumed outbound contracts in `integration/rsl_sinks` ([ADR-048](../../docs/decisions/ADR-048-outbound-results-to-rsl.md)). `rules.py` is Frappe-free (RSL reference, approval checks, findings pack, lane recommendation, evidence notice, delivery states). `store.py` queues an outbox event (`rsl_outbound.requested`) and a ledger entry when a decision is approved or an evidence request is authorised, delivers through the outbox effect ledger to the site's sink (`vati_rsl_sinks`) and records the delivery. `api.py` has the officer read `get_case_outbound`.
- `vati_tax/refund_access` (TAX-142) keeps refund cases confidential ([ADR-049](../../docs/decisions/ADR-049-refund-confidentiality.md)): only service identities, refund-team supervisors and the assigned refund-team officer read a refund case. `store.py` is the gate every case-scoped endpoint and /api/v1 call passes (refusals are sealed into the audit ledger), plus `Vati Case Assignment` handling; `identity/permissions.py` applies the same rule to Desk. `api.py` has `assign_case` and `get_case_assignment`.
- `vati_tax/evidence_gaps` (TAX-127) builds evidence requests that ask only for the gap ([ADR-050](../../docs/decisions/ADR-050-gap-only-evidence-requests.md)). `rules.py` is Frappe-free: from RSL's claim lines and the lane proposal's TAX-112 `line_match` it lists the lines RSL already holds and itemises only the unmatched ones (answers `confirm`, `dispute`, `attach_proof`). `store.py` has `propose_gap_request` (computed, officers only) and `approve_gap_request`, which records the request through the TAX-046 authorisation and stores the line detail. `api.py` whitelists both.
- `vati_tax/prefiling` (TAX-129) is the check before you file ([ADR-051](../../docs/decisions/ADR-051-check-before-you-file.md)). `rules.py` is Frappe-free: from the taxpayer's e-Tax return, Lekuka invoices and ASYCUDA entries for a period it gives guidance only (no lane, score or block) and links to RSL's Online Refunds Application. `store.py` reads them through the site's RSL source and runs the TAX-048 return arithmetic through `portal.presubmission`. The taxpayer portal calls `portal.api.check_before_filing`; RSL's front door calls `prefiling.api.check_before_filing` as a service identity.
- `vati_tax/references` (TAX-133) is the case reference card ([ADR-052](../../docs/decisions/ADR-052-rsl-reference-register.md)). The RSL systems (`online_refunds`, `audit_system`, `psrm`, `etax`, `idms`, `asycuda`) are services in `ids.canonical` with the same tenant and conflict rules; the referral and Online Refunds intakes record the audit case and claim links, and patch `v0_4.link_rsl_references` backfills older ones. `rules.py` is Frappe-free and builds the officer or taxpayer view; `store.py` reads the register. Officers call `getCaseReferences`; taxpayers call `portal.api.get_case_references` with their own submission or evidence request.
- Referred cases only (TAX-131, [ADR-053](../../docs/decisions/ADR-053-jube-and-vati-risk-downstream-of-rsl.md)). `submissions.domain.referred_source` lets only a claim read from RSL's Online Refunds Application be sent, or a portal send where the Online Refunds simulator stands in for RSL. Other sends are refused, and the send hooks open no case and never call Jube. `api_v1.projections.rsl_selection_reasons` shows RSL's referral reason, risk-set scores and refund-model score as RSL's. `ai.evaluation.risk_unit_feedback` exports TAX-066/067 output as aggregate feedback for RSL's Risk Unit.
- Lanes against RSL's claim status (TAX-132, [ADR-054](../../docs/decisions/ADR-054-lanes-against-rsl-claim-status.md)). Each lane proposal records the status RSL reported (`rsl_claim_status`). No lane is proposed for a claim RSL has processed, rejected or cancelled. The `lane_recommendation` to RSL carries the status at proposal and is not queued if RSL has decided the claim since.
- `vati_tax/api_v1` (TAX-090) is the live `/api/v1` service for the auditor app ([ADR-046](../../docs/decisions/ADR-046-vati-api-v1-in-frappe.md)). `core.py` is the Frappe-free router (contract request rules from `integration/api/contract.py`, ADR-003 errors, keyset paging, officer UUIDs), `projections.py` the pure record-to-contract mappings, `management.py` the summary rules shared with the fixture server, `operations.py` the served operations, `backend.py` the Frappe handlers and `api.py` the whitelisted `route` method (`/api/method/vati_tax.api_v1.api.route?path=/api/v1/...`). TAX-088 registers its briefing reader in the `vati_briefing_reader` hook.

Tests named `test_*.py` must pass under plain `unittest` without a site. Site-backed tests skip themselves there and run on the disposable `verify` site via `bench run-tests --app vati_tax`.

- `vati_tax/submissions` (TAX-031) holds the taxpayer and submission rules: `domain.py` (pure money, period, status and field-write rules), `guard.py`/`declaration.py` (controller adapters) and the `Vati Taxpayer`, `Vati Submission`, `Vati VAT Return`, `Vati Refund Claim` and `Vati Imported Service` DocTypes ([ADR-010](../../docs/decisions/ADR-010-submission-doctypes.md)).

TAX-032 and TAX-033 add evidence and the outbox; give their DocTypes `tenant_id`/`taxpayer_id` fields and role permissions, and add negative tests.
