TAX-022 provides typed investigation state, case-scoped tool result envelopes, and a deterministic fake-tool LangGraph. It makes no live service calls and performs no tax assessment or enforcement action.

For the model-free graph, construct state with `create_investigation_state(...)` and invoke `build_fake_tool_graph()`. The state factory requires tenant, case and run IDs and limits each run to at most eight tool calls. Tool failures are returned in the error envelope and stop execution for human review.

TAX-048 adds `ai/tools/refund_reconciliation.py` (Decimal-only claimed/explained/unresolved refund reconciliation over synthetic records) and `ai/workflows/refund_lanes.py` (a case-scoped tool plus `reconcile -> propose_lane` nodes). The fast/standard/targeted lane is an advisory proposal with `decision: null` that always requires officer approval; thresholds are prototype choices documented in the module, not RSL policy.

TAX-050 adds `ai/tools/imported_services.py` and `ai/workflows/imported_services_playbook.py`. Charges marked as imported services (explicit `supplier_residence: "non_resident"` or the TAX-024 `vat_status: "treatment_unverified"` marker; never inferred from names) are traced contract -> invoice -> payment (+ declared withholding) -> declared VAT/withholding treatment with Decimal amounts. Missing records become gaps, contradictory records discrepancies, and each gap drafts a neutral, evidence-linked question for officer approval. Statutory treatment is always `unverified_pending_expert_review`; the advisory finding (`code: imported_service_treatment_unverified`) is compatible with the TAX-052 policy-gap gate, which reports the legal route separately and blocks enforcement conclusions.

TAX-047 adds `ai/workflows/human_checkpoints.py` (ADR-014). Runs persist in a SQLite checkpoint file you pass explicitly (`open_checkpointer(path)`) and interrupt before any consequential action. `resume_with_approval` continues only for the authenticated supervisor who approved the matching TAX-046 decision, bound to tenant, case, draft, case version and the SHA-256 of the exact action payload; refusals leave the run paused. Approved actions go through an injected idempotent `ApprovedActionPort`, so `recover_run` after a worker crash cannot apply an action twice. The worker never calls Jube or Frappe directly.

TAX-049 adds `ai/tools/related_party.py` and `ai/workflows/related_party_playbook.py`. For each disclosed related-party contract it tests the relationship, service delivery, benefit, possible duplication (same service category/description or repeated billing) and the payment trail; for three or more consecutive loss quarters it looks for documented alternative explanations. Every observation, gap, discrepancy and item of counter-evidence cites IDs that resolve to case records (`record.documents` may list supporting documents). Unsupported services are evidence gaps with neutral questions, never conclusions; pricing, intent and treatment are not assessed. `ai/workflows/record_playbook.py` holds the case-scoped record tool and review -> propose graph shared with TAX-050.

TAX-051 adds `ai/tools/work_arrangement.py` and `ai/workflows/work_arrangement_playbook.py`. Cited contract, work-evidence and statement facts are grouped by a neutral factor checklist (not a weighted legal test) and marked unknown, consistent or conflicting; the payment pattern is derived from invoices. A contract with an `unresolved` classification or conflicting facts is referred: the run persists the structured facts in the TAX-047 SQLite checkpoint and pauses. Only an authenticated specialist (TAX-046 `specialist.opinion.record`), bound to tenant, case, case version and the SHA-256 of the facts reviewed, can resume and record an attributed opinion; the agent never classifies or assesses, and an officer decision is still required.

TAX-061 adds the approved tool/playbook registry (`ai/workflows/playbook_registry.py`, `playbook_registry.synthetic.json`, ADR-017). Each version pins approval status, allowed operations, provenance requirements, tool references and a SHA-256 of its source files; `run_playbook` runs only approved, digest-matching versions, stamps findings with provenance and returns a replayable run record (`replay_run`). Editing a registered source file makes that version unapproved: run `python -m ai.workflows.playbook_registry` and update the registry in the same reviewed PR. Approvals are synthetic placeholders; real activation needs supervisor `playbook.approve`, holdout evaluation and rollback.

TAX-064 adds `ai/workflows/workflow_observation.py`. It reads one tenant's TAX-059 audit-ledger entries (`entry_view` shape, optionally enriched with the approved decision outcome as `detail`) and keeps only approved work: authorised evidence requests and approved decisions that were not followed by a failed execution. Reads, refusals, overrides, drafts, rejections and withdrawals never become steps, and an unrecognised `detail` is not trusted as a step name. Cases are split deterministically into training and held-out sets; contiguous sequences seen in at least 3 training cases across at least 2 distinct actors become versioned `workflow_proposal` records with `status: proposed`, `auto_activate: false` and supporting ledger event IDs, each compared descriptively with the held-out traces (coverage, follow rate, divergences). Thresholds are prototype choices. Nothing in the module can activate a workflow (`activate` refuses); activation needs supervisor `playbook.approve`, a reviewed TAX-061 registry entry and a rollback plan.

TAX-066 adds `ai/evaluation/risk_calibration.py` (ADR-030). It evaluates the approved TAX-035 risk ruleset against reviewed outcomes read from TAX-059 ledger entries (a decision proposed by one officer, approved by a different supervisor with the outcome joined as `detail`, executed, and not overturned on challenge; anything else is excluded with a reason). `close_no_further_action` counts as legitimate; the other allowlisted outcomes count as review warranted. A candidate is fitted on earlier calibration periods only (labels approved before `label_cutoff`) and evaluated on later holdout periods: false positives and misses are listed by case, legitimate-case regressions and newly missed review-warranted cases block promotion, and drift (rule fire rates, label mix, feature PSI) is reported per window and period. The candidate is `status: proposed_calibration` with `auto_activate: false`; `promote` only returns an approval record when a `SYN-SUPERVISOR-NN` other than the proposer approves the exact candidate, parent and report digests and acknowledges every drift alert, and never when the metric gate is blocked. Nothing writes the approved ruleset. `python -m ai.evaluation.risk_calibration --check` fails CI when the report leaves the reviewed baseline in `data/synthetic/tax066_reviewed_outcomes.json`. Results: `docs/evidence/TAX-066/README.md`.

TAX-053 adds `ai/tools/evidence_search.py` and `ai/workflows/case_briefing.py` (ADR-021). The search refuses callers without `evidence.read` in the tenant before reading any document, searches only the active tenant and case (latest versions with completed extraction) and returns citation IDs that expand to contract `EvidenceRef`s. The briefing graph (`search_evidence -> draft_briefing`) asks a `BriefingModel` for five sections (what happened, what was checked, what is explained, what is unresolved, next action) and validates the draft: every statement must cite a reference that resolves to this run, questions without evidence are missing information (never discrepancies), conclusions and actions that aren't allowlisted are rejected with a reason, and next actions always need officer approval. Document text reaches the model only in a fenced `untrusted_evidence` block; instruction-like text is flagged as unresolved and changes nothing. The default model is deterministic and template-based; a hosted model needs approval and the TAX-056 evaluation first.

TAX-056 adds `ai/evaluation/agent_eval.py` (ADR-029), the independent evaluation and injection regression harness. It runs every approved playbook, the policy-gap gate, the cited briefing and the approved-action checkpoint against the five TAX-024 scenarios (3 runs each) and against hostile fixtures in `data/synthetic/tax056_evaluation_fixtures.json`. It reports expected output, false positives, citation coverage, interrupt compliance, hostile resistance and determinism per subject, and lists every failed check by ID. `python -m ai.evaluation.agent_eval --check` fails CI on a new failure or on a known failure that no longer occurs. A change to a playbook, prompt or model must keep this gate passing; a hosted model must pass it before approval. Results: `docs/evidence/TAX-056/README.md`.

TAX-068 adds `ai/workflows/institutional_knowledge.py`. `build_index` keeps only independently reviewed outcomes (TAX-046 decisions with status `approved`, reviewed by a supervisor who did not propose them) with their reasoning, accepted alternatives, cited `EvidenceRef`s and the legal authority versions recorded at decision time. `retrieve` applies the TAX-053 read-access rule before anything is read, then a required, deny-by-default `can_read_case` check per case; restricted records are supervisor-only, the active case is never returned and other taxpayers' identifiers are omitted. Every result is `nature: institutional_memory`, `binding: false`, and each cited authority version is re-checked against the current TAX-052 registry (in force, no longer in force, unverified, unknown). Instruction-like reasoning text is flagged, never obeyed.

TAX-071 adds `ai/workflows/eoi_drafting.py`. `draft_eoi_package` (TAX-053 read-access check first) builds a draft exchange-of-information package for competent-authority review from the TAX-050 imported-services review: per foreign counterparty it cites the domestic contract/invoice/payment records, lists missing foreign facts (jurisdiction when not declared, identity and registration, tax residence, services and location unless already recorded, consideration received, relationship to the taxpayer) and lists open taxpayer questions as outstanding domestic steps. The legal basis is looked up in the TAX-052 registry (`eoi_request`) and is never asserted (`instrument: null`). The package is `status: draft` with `transmission.enabled: false`; `transmit` always refuses and the module imports no network library. TAX-072 owns approval, lawful channels and responses.

TAX-067 adds `ai/workflows/peer_baselines.py`. `compare` (TAX-053 read-access check first) compares one taxpayer-period with the taxpayer's own earlier periods (at least 4) and with peers in the same sector, size band and period (at least 10), using Decimal ratios (refund/turnover, input VAT/turnover), nearest-rank median/IQR, percentile rank and a plain-language explanation with sample size and data-quality notes. Small samples, more than 20% data-quality exclusions (incomplete, amended-unreconciled, unverified source), a peer group over 80% from one region, or an undefined ratio give `insufficient_evidence` with reasons. `outside_typical_range` comes with ordinary alternative explanations; `risk_score` and `fraud_conclusion` are always null and only aggregates are returned (no peer identities).

TAX-070 adds `ai/workflows/outcome_feedback.py`. `evaluate_feedback` reads TAX-069 challenge histories joined with the provenance that informed each decision (TAX-061 playbook/tool stamps, risk rule versions, TAX-052 authority versions) and attributes reviewed final outcomes to each component version; withdrawn and unresolved challenges are excluded with reasons and a history whose original decision changed is reported as a lineage problem, not counted. A component version with at least 3 final outcomes and an overturn share of at least 1/2 becomes a `component_review_proposal` (or, for a legal authority, a `legal_review_referral` with `legal_interpretation_change: null`), citing overturned cases and upheld counter-evidence, with its evaluation lineage and a reproducible lineage digest. Proposals are `status: proposed`, `auto_apply: false`; `apply` always refuses, so nothing changes a rule, playbook, registry or legal interpretation.

TAX-075 adds `ai/workflows/network_patterns.py`. `detect_patterns` (TAX-053 read-access check first) reads one tenant's TAX-074 case graphs and finds recurring structures: a shared intermediary or adviser across at least 3 cases, a common beneficial owner across at least 2, a scheme linked to at least 3 cases, and circular ownership inside a case. Each pattern lists its supporting edges with provenance and evidence citations, is marked novel when absent from the baseline graphs, and is queued for analyst review only if every supporting case has cited evidence; otherwise it is `insufficient_evidence` with its source gaps. Novelty alone is never sufficient, no party is labelled or scored and `enforcement_action` is always null. `evaluate_reviews` reports false-positive and source-gap shares per pattern type from analyst outcomes.

TAX-080 adds `ai/workflows/playbook_extensions.py` and `playbook_extensions.synthetic.json` (ADR-033). These hold design-stage extension contracts for PAYE, withholding, treaty/permanent-establishment facts and digital services. Each contract names its required sources (system of record and v1 status), a legal-review gate (RSL legal reviewer role, open questions, reviewer) and six independent evaluation fixtures (legitimate, missing, contradictory, hostile, no verified route, cross-tenant). It also lists the deterministic checks, `get_model` roles, allowed operations, provenance, finding codes, alternative explanations and budgets. No law, rate or threshold is encoded. `readiness` computes blockers: sources not in v1, a pending legal review, finding codes absent from the TAX-052 registry, fixtures not yet authored in `data/synthetic/tax080_domain_fixtures.json`, and pending contract categories. `check_registry` refuses a TAX-061 playbook entry for a domain that still has blockers. ## Model router (TAX-089, ADR-031)

`ai/models/` provides `get_model(role)` for `reasoning`, `fast` and `document`. Agents use only `get_model`; graphs, tools and the evaluation never import `ai.models.providers`/`ai.models.config`, a provider SDK or read a key (`tests/ai/test_model_router.py` checks this). The returned `RoutedModel` satisfies the TAX-053 `BriefingModel` port (`model_id`, `config`, `draft(request)`) and offers `complete(CompletionTask)` for structured JSON output: trusted `instructions`, a JSON `payload` (callers fence untrusted text in it), a deterministic `template`, an optional `validate` (returns a reason code or `None`) and an optional mock `fixture`.

Each call walks a chain: level 0 is the hosted model (Groq `openai/gpt-oss-120b` for `reasoning`, `openai/gpt-oss-20b` for `fast`, Gemini for `document`) or the `mock` fixture provider; level 1 is the optional local Ollama model; level 2 is the deterministic template. HTTP 429, timeouts, refusals, invalid or truncated JSON, other HTTP or connection failures, exhausted call/token/input budgets and failed validation each move the call down one level. Every output carries `provenance`: provider, observed and configured model ID, role, task, prompt version, settings (temperature, max output tokens, timeout), fallback level, every attempt with its outcome, latency, token use, rate-limit headers and the validation result. For the briefing, provenance lands in the existing record as `model.config.provenance` and `model.id` is the model actually used; a hosted draft must pass `validate_draft` with no rejected statement or the call falls back, and the graph still validates the result. HTTP uses stdlib `urllib`, so no packages were added. Use one `RoutedModel` per run: its call and token budgets and last provenance are per instance.

Configuration comes only from the environment and the ignored `.env` (only the keys in `.env.example` are read). `VATI_MODEL_PROVIDER` is `mock` (default; unset or unknown values also give mock, no network), `hosted`, `local` or `template`. In `hosted` mode a role without its key uses `mock`. Model IDs default to ADR-031 (accepted 2026-11-05) and `.env.example`: `openai/gpt-oss-120b`, `openai/gpt-oss-20b` and, for `document`, the team-confirmed `gemini-3.6-flash` (`gemini-2.5-flash` is deprecated). Setting a role variable such as `VATI_MODEL_DOCUMENT=none` leaves that hosted level `unconfigured`, so the role falls down the chain. Record the Gemini model's context window and observed free-tier limits with the live smoke. Keys are wrapped in `Secret` and never appear in `repr`, records or errors; send only synthetic data to free tiers.

To enable live models put `VATI_MODEL_PROVIDER=hosted`, `GROQ_API_KEY` (and `GEMINI_API_KEY` for the `document` role) in your ignored `.env`. Optionally set `OLLAMA_BASE_URL=http://127.0.0.1:11434` and `VATI_MODEL_LOCAL`. `python -m ai.models.smoke` runs every role offline in mock mode; `python -m ai.models.smoke --live` (or `VATI_LIVE_MODEL_SMOKE=1 python -m unittest tests.ai.test_model_router`) sends one tiny synthetic prompt per configured hosted role and prints the observed model ID, latency, tokens and rate-limit headers, skipping unconfigured roles. Routed models in agent reasoning are TAX-097 (below); `agent_eval --check` must keep passing.

## Model-assisted interpretation (TAX-097, ADR-031)

`ai/workflows/interpretation.py` lets the four investigation agents use routed models for interpretation only. The refund-lane graph (`build_refund_lane_graph(tool, models=get_model)`) and the related-party graph add an `interpretation` to their deterministic finding from the `reasoning` role; the briefing graph (`build_briefing_graph(tool, evidence_source=..., models=get_model)`) drafts with the `reasoning` role and records an `evidence_interpretation` of the cited contract, invoice and extracted (Docling) text from the `fast` role, using `document` only when the fenced text is longer than `LONG_DOCUMENT_CHARS`. Without `models` the playbooks stay model-free, and the registry builders pass `build_options["models"]` through. Amounts, thresholds, lanes, codes and questions still come only from the deterministic tools and are never changed by a model.

An interpretation is a list of `explanation`, `hypothesis`, `alternative_explanation` and `open_question` statements, each citing IDs from the deterministic result (or this run's search hits). It is validated inside the router call, so a failure falls back to the deterministic template, and is validated once more afterwards. It is rejected when it states a number that the tools did not produce (`figure_not_in_results`; for evidence and briefing statements, `figure_not_in_evidence`: the number must be in the text the statement cites), a refund, lane or case decision, an accusation, a legal conclusion or tax treatment, or instruction-like text, when it cites an unknown ID or only text flagged as instruction-like, or when it offers hypotheses without an alternative. Record and document text reaches the model only in the fenced `untrusted_evidence` block. Each output keeps the router's full record as `router_provenance` and carries `analysis_provenance` and `disclosure` projected onto the TAX-096 contract shapes (`ai.models.to_contract_provenance` and `to_disclosure`: `token_usage`, contract attempt fields, scalar settings with decimal strings, no rate-limit headers or notes). Briefings now carry both fields too, including template-only ones.

`get_model(role, offline=True)` ignores the environment and returns the keyless mock chain. `python -m ai.evaluation.agent_eval --check` always uses it, so the gate stays offline even when a local `.env` enables hosted models. The harness also scores every interpretation: it must be validated, cite only the case's records, give alternatives when the finding carries a risk code, state no figure the tools did not produce, leave decisions empty, and leave the deterministic finding identical to a model-free run. `python -m ai.evaluation.agent_eval --live --json out.json` is the opt-in live variant. It uses `get_model(role)` as configured, is paced to stay under Groq's published 8,000 tokens/min, and lists every model call with scenario, run, provider, model, fallback level, latency, tokens and validation. Results: `docs/evidence/TAX-097/README.md`.
